# Ralph Loop — правила автономной сессии

Эти правила действуют только внутри Ralph Loop. Обычные сессии Codex
их не получают.

## Как брать issue

- Прочитай title, body и все критерии готовности issue.
- Сверь требования issue с кодом, документацией и правилами AGENTS.md.
- Работай только над issue #{issue_number}. Не включай в commit посторонние
  изменения.
- Не изменяй `.agents/**`, `scripts/ralph/**`, корневой или вложенный `AGENTS.md`.
  Это служебная инфраструктура Ralph, которую оператор настраивает вручную вне
  продуктового цикла. Если issue требует таких изменений, остановись и сообщи блокер.
- Если требования противоречивы или небезопасны, не угадывай: остановись
  и опиши блокер.

## Правила работы с веткой

- Целевая ветка: `{branch}`.
- Оркестратор уже проверил ветку до запуска. Не переключай ветки и не
  создавай новых.
- Не выполняй merge, rebase, reset, force-push или другие опасные Git-операции.
- Не выполняй команды, которые изменяют Git: не делай `git add`, `git commit`,
  `git restore`, `git stash` и не меняй ветку. Оркестратор сам создаст commit.
- Не запускай `gh` и не изменяй GitHub issue. Оркестратор работает с GitHub вне
  sandbox после проверок и независимого review.
- Не создавай PR. Его создаёт оркестратор, когда в milestone не останется
  открытых issues.

## Правила реализации

- Сессия имеет жёсткий лимит `{max_turns}` наблюдаемых шагов Codex. Оркестратор
  принудительно остановит сессию при попытке превысить этот лимит. Не расширяй
  объём задачи: сначала доведи до готовности обязательные требования issue.
- Для изменений поведения используй TDD: сначала добавь или измени тест и убедись,
  что он падает по ожидаемой причине; затем реализуй минимальное изменение.
- Для чистой документации, конфигурации или рефакторинга без изменения поведения не
  создавай искусственный тест; выполни релевантные проверки.
- После каждого финального изменения снова запусти затронутые тесты и быстрые
  проверки, относящиеся к изменённому workspace.
- Не ослабляй и не удаляй тесты ради зелёного результата.
- Если после `{max_test_fix_attempts}` осмысленных попыток тесты остаются красными, остановись.
  В финальном сообщении укажи, какая команда падает, ключевой фрагмент ошибки, что уже
  пробовалось и какой следующий шаг предлагается. Не меняй GitHub issue.

## Проверки внутри sandbox

- Во время TDD запускай минимальный затронутый test-файл или узкий набор тестов.
  Не запускай весь список `validationScripts`: после завершения сессии оркестратор
  выполнит его снаружи sandbox перед commit и review.
- Не запускай полные `test:ralph`, API E2E и Web E2E только ради общей проверки.
  Если issue непосредственно меняет соответствующую подсистему, запускай самый
  узкий релевантный набор. Полный прогон всё равно выполнит оркестратор.
- На Windows вызывай npm scripts через `npm.cmd`, а не через PowerShell-обёртку
  `npm.ps1`, которой sandbox может запретить чтение пользовательского npm prefix.
- В PowerShell передавай найденные файловые пути в `Get-Content`, `Get-Item` и
  другие file cmdlets через `-LiteralPath`. Динамические Next.js-сегменты вроде
  `[id]` не должны интерпретироваться как wildcard-шаблоны.
- Если тесты уже сообщили PASS, но процесс не завершился из-за оставшихся
  dev-серверов, зафиксируй это как ограничение среды. Не повторяй тот же полный
  прогон с увеличенным таймаутом: внешний оркестратор проверит его отдельно.

## Сообщение для commit

- Не создавай commit самостоятельно.
- Если ты оставил изменения, последней строкой финального сообщения предложи
  сообщение в формате `COMMIT_MESSAGE: <type>: <краткое описание>`, например
  `COMMIT_MESSAGE: feat: add profile endpoint`.
- Если issue уже полностью исправлена существующим commit текущей ветки, не
  создавай искусственное изменение. Убедись, что именно этот commit содержит
  исправление, является предком текущего HEAD и удовлетворяет всем требованиям
  issue. Запусти проверки и вместо `COMMIT_MESSAGE` последней строкой укажи
  `ALREADY_FIXED: <полный или короткий SHA commit>`. Не используй случайный SHA,
  merge-base или commit только ради обхода отсутствующего diff: оркестратор
  проверит commit и отправит его на независимый review.
- Разрешённые типы: `feat`, `fix`, `docs`, `test`, `refactor`, `perf`, `build`,
  `ci`, `chore`. Оркестратор проверит строку и создаст один commit.

## Правила завершения

Перед завершением сессии:

- сверь каждое требование и критерий готовности issue с результатом;
- убедись, что все затронутые тесты и разрешённые быстрые проверки зелёные;
- проведи self-review текущего `git diff`: ищи ошибки, регрессии, нарушения безопасности,
  непокрытые граничные случаи и невыполненные требования; исправь найденное и повтори
  проверки;
- оставь только относящиеся к issue изменения в рабочем дереве, не добавляя
  локальные артефакты, секреты или чужие изменения;
- не закрывай issue и не создавай GitHub-комментарии;
- не создавай PR.

После завершения оркестратор прогонит полный список обязательных проверок вне
sandbox, создаст commit, запустит независимый
Terra-review и только после PASS закроет issue. Если review найдёт проблемы, issue
останется открытой, review-контекст будет добавлен в её body, а `--run` продолжит
цикл исправления до PASS или circuit breaker. Технически прерванный review
возобновится для уже созданного commit без повторной реализации. Когда закроются все issues milestone,
оркестратор создаст draft PR и запустит отдельный Sol-review всего diff фазы.
