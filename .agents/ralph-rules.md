# Ralph Loop — правила автономной сессии

Эти правила действуют только внутри Ralph Loop. Обычные сессии Codex
их не получают.

## Как брать issue

- Прочитай title, body и все критерии готовности issue.
- Сверь требования issue с кодом, документацией и правилами AGENTS.md.
- Работай только над issue #{issue_number}. Не включай в commit посторонние
  изменения.
- Если требования противоречивы или небезопасны, не угадывай: остановись
  и опиши блокер.

## Правила работы с веткой

- Целевая ветка: `{branch}`.
- Оркестратор уже проверил ветку до запуска. Не переключай ветки и не
  создавай новых.
- Не выполняй merge, rebase, reset, force-push или другие опасные Git-операции.
- Не выполняй команды, которые изменяют Git: не делай `git add`, `git commit`,
  `git restore`, `git stash` и не меняй ветку. Оркестратор сам создаст commit.
- Не запускай `gh` и не изменяй GitHub issue. Оркестратор работает с GitHub вне
  sandbox после проверок и независимого review.
- Не создавай PR. Его создаёт оркестратор, когда в milestone не останется
  открытых issues.

## Правила реализации

- Сессия имеет жёсткий лимит `{max_turns}` наблюдаемых шагов Codex. Оркестратор
  принудительно остановит сессию при попытке превысить этот лимит. Не расширяй
  объём задачи: сначала доведи до готовности обязательные требования issue.
- Для изменений поведения используй TDD: сначала добавь или измени тест и убедись,
  что он падает по ожидаемой причине; затем реализуй минимальное изменение.
- Для чистой документации, конфигурации или рефакторинга без изменения поведения не
  создавай искусственный тест; выполни релевантные проверки.
- После каждого финального изменения снова запусти затронутые тесты и обязательные
  проектные проверки.
- Не ослабляй и не удаляй тесты ради зелёного результата.
- Если после `{max_test_fix_attempts}` осмысленных попыток тесты остаются красными, остановись.
  В финальном сообщении укажи, какая команда падает, ключевой фрагмент ошибки, что уже
  пробовалось и какой следующий шаг предлагается. Не меняй GitHub issue.

## Сообщение для commit

- Не создавай commit самостоятельно.
- Последней строкой финального сообщения предложи сообщение в формате
  `COMMIT_MESSAGE: <type>: <краткое описание>`, например
  `COMMIT_MESSAGE: feat: add profile endpoint`.
- Разрешённые типы: `feat`, `fix`, `docs`, `test`, `refactor`, `perf`, `build`,
  `ci`, `chore`. Оркестратор проверит строку и создаст один commit.

## Правила завершения

Перед завершением сессии:

- сверь каждое требование и критерий готовности issue с результатом;
- убедись, что все затронутые тесты и обязательные проверки зелёные;
- проведи self-review текущего `git diff`: ищи ошибки, регрессии, нарушения безопасности,
  непокрытые граничные случаи и невыполненные требования; исправь найденное и повтори
  проверки;
- оставь только относящиеся к issue изменения в рабочем дереве, не добавляя
  локальные артефакты, секреты или чужие изменения;
- не закрывай issue и не создавай GitHub-комментарии;
- не создавай PR.

После завершения оркестратор прогонит проверки, создаст commit, запустит независимый
Terra-review и только после PASS закроет issue. Если review найдёт проблемы, issue
останется открытой, а цикл остановится. Когда закроются все issues milestone,
оркестратор создаст draft PR и запустит отдельный Sol-review всего diff фазы.
