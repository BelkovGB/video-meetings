# Ralph Loop для Codex

Codex не использует Claude Code `Stop` hook. В этом проекте
циклом управляет внешний Node.js-скрипт `scripts/ralph/ralph-loop.mjs`.
Файл `.agents/ralph-loop.mjs` — только совместимый launcher для старой команды.
Исполняемый код находится в `scripts/ralph`, но вместе с `.agents/**` и всеми
`AGENTS.md` относится к защищённому control plane. Продуктовый AFK-цикл никогда
не изменяет эти файлы: Ralph настраивается и исправляется оператором в отдельном
чате, а не собственными issues.
Правила автономной сессии хранятся отдельно в `.agents/ralph-rules.md` и
добавляются в prompt только при запуске Ralph Loop.

## Перед запуском

1. В `.agents/ralph.config.json` заполнить массив `phases` в порядке выполнения.
   Для каждой фазы указать **точное** название GitHub milestone и отдельную
   рабочую ветку `branch`.
2. Проверить глобальный `baseBranch`. При необходимости конкретная фаза может
   переопределить его своим `phases[].baseBranch`.
3. Убедиться, что история каждой рабочей ветки совместима с её базой PR.
4. Проверить `docker version`, авторизацию `gh auth status` и `codex --version`.
5. Убедиться, что рабочее дерево чистое либо содержит только незавершённую
   работу, сохранённую самим Ralph для восстановления.

Перед автономной работой Ralph выполняет scripts из `preflightScripts` в
отдельных непривилегированных validation-контейнерах без сети и host credentials.
Контейнер сам запускает временный PostgreSQL и создаёт одноразовый локальный
Git-репозиторий из проверяемого snapshot без host metadata или credentials;
`db:ready` сохраняется как healthcheck-контракт через безопасный Docker shim, а
`db:migrate` применяет уже существующие Prisma migrations. Prisma Client и Linux engine заранее создаются
при сборке образа, после чего образ без сети повторно генерирует client и
применяет migrations. Полная сборка выполняется позднее с проверяемым снимком
исходников в таком же контейнере без сети. Если окружение не готово, разработка
не начинается.

В режимах `--once` и `--run` скрипт сам перейдёт на ветку текущей фазы. Если её нет
локально, он подключит удалённую ветку или создаст новую от её `origin/baseBranch`.
При грязном рабочем дереве это запрещено. `--check` ничего не переключает и не
создаёт.

## Несколько фаз

`phases` — упорядоченный массив независимых фаз. Пример:

```json
"phases": [
  {
    "milestone": "Phase 1: Core Profile API",
    "branch": "features/profile-phase-1"
  },
  {
    "milestone": "Phase 2: Profile UI",
    "branch": "features/profile-phase-2",
    "baseBranch": "master"
  }
]
```

В режиме `--run` Ralph полностью завершает текущую фазу: закрывает её issues,
создаёт отдельный PR, получает чистый milestone-review и закрывает milestone.
Только после этого он сохраняет следующий `phaseIndex`, обнуляет счётчик
`maxIterations` для новой фазы, переключает ветку и продолжает работу. После
сбоя следующий запуск возобновляет сохранённую фазу, а не начинает план заново.

Фазы считаются независимыми и по умолчанию создаются от глобального
`baseBranch`. Если следующая фаза действительно зависит от ещё не смерженной
предыдущей ветки, её `baseBranch` нужно задать явно; Ralph не выполняет merge PR
автоматически. Названия milestone и веток в массиве должны быть уникальными.

Старый однофазный формат с верхнеуровневыми `milestone` и `branch` по-прежнему
поддерживается и автоматически воспринимается как массив из одной фазы.

## Что происходит в одной итерации

1. Скрипт получает title, body и URL следующей issue.
2. В prompt подставляются issue, branch, milestone, лимит попыток и
   содержимое `.agents/ralph-rules.md`.
3. Оркестратор считает уникальные `item.started`/`item.completed` из `codex exec --json`.
   Служебные items типа `error` не учитываются. При попытке начать шаг после
   `maxTurns` дочерний процесс Codex принудительно завершается.
4. Codex на модели из `developmentModel` (`gpt-5.6-terra`) запускается с
   `danger-full-access`: может редактировать и создавать файлы во всём рабочем
   дереве, реализует задачу по TDD, запускает только затронутые тесты и быстрые
   проверки, делает self-review. GitHub credentials ему не передаются, а
   изменения доверенных control-файлов Ralph и `AGENTS.md` оркестратор отклоняет
   до commit.
5. Скрипт проверяет ветку и изменения, запускает полный список обязательных
   проверок вне development sandbox, но внутри изолированных validation-контейнеров,
   создаёт ровно один commit и отправляет его в удалённую ветку.
6. Только для уже опубликованного commit отдельный read-only `codex exec` на модели `review.model`
   (`gpt-5.6-terra`) проверяет созданный commit и пишет
   структурированный результат в `.agents/last-review.json`.
7. Только после успешного review опубликованного commit оркестратор закрывает
   issue через GitHub CLI.
8. При замечаниях review issue остаётся открытой, в неё добавляется комментарий,
   и `--run` передаёт её Terra на следующей итерации. Техническая ошибка review
   повторяется согласно `runtime.reviewRetryAttempts`; если попытки исчерпаны,
   commit сохраняется в состоянии issue. Следующий `--run` повторит проверки и
   review без повторной реализации. Служебная
   отметка в issue не считается доказательством успеха сама по себе и удаляется
   перед успешным закрытием issue.

Каждый созданный Ralph commit содержит trailer `Ralph-Issue: #<number>`. Если
процесс был остановлен, а готовый commit появился отдельно, следующий запуск
свяжет его с issue и сразу перейдёт к полным проверкам и review без повторной
Terra-сессии. Автоматически принимается только commit новее последнего изменения
issue: старый trailer после нового review или ручного reopen не переиспользуется.

## Что происходит после завершения milestone

1. Когда открытых issues больше нет, скрипт выполняет все финальные npm-проверки,
   отправляет ветку и создаёт draft PR (либо находит уже открытый PR этой ветки).
2. Модель из `milestoneReview.model` (`gpt-5.6-sol`) проверяет целостность всей
   текущей фазы. Diff относительно `baseBranch` используется как доказательство,
   но границы review задаются title и description текущего milestone: накопленные
   изменения других фаз не должны превращаться в его issues.
3. В review учитываются архитектура, взаимодействие изменений из разных issues,
   безопасность, производительность, масштабирование, тесты и соответствие PRD.
4. Sol возвращает структурированный JSON в
   `.agents/last-milestone-review.json`; только оркестратор публикует его в PR
   через GitHub CLI.
5. При FAIL оркестратор создаёт по одной issue на каждый **продуктовый** finding в текущем
   milestone. Повторный finding не создаёт дубликат: существующая открытая issue
   используется снова, а закрытая переоткрывается. Только что созданные issues
   сразу добавляются во внутреннюю очередь, поэтому цикл не зависит от задержки
   обновления GitHub API. За один review создаётся не больше
   `milestoneReview.maxFindings` задач. Findings по `.agents/**`,
   `scripts/ralph/**` и любым `AGENTS.md` исключаются из продуктовой очереди и
   разбираются вручную в чате настройки Ralph.
6. Terra последовательно исправляет review-issues, после чего ветка отправляется
   заново и Sol проверяет новый SHA. Цикл продолжается до PASS либо до достижения
   `maxIterations`/`maxTurns`.
7. После чистого PASS оркестратор закрывает GitHub milestone. PR остаётся draft:
   окончательное решение о merge принимает человек. Если в `phases` есть следующий
   элемент, Ralph сохраняет переход и запускает его в отдельной ветке.
8. Повторный `--run` не расходует токены на уже опубликованный PASS того же SHA:
   скрипт ищет в PR
   скрытый маркер с моделью и SHA. После нового commit SHA изменится, и Sol
   выполнит review заново.

## Команды

```powershell
# Только проверить конфиг, GitHub, milestone и ветку
node scripts/ralph/ralph-loop.mjs --check

# Выполнить ровно одну issue и остановиться
node scripts/ralph/ralph-loop.mjs --once

# Выполнить issues, создать draft PR и запустить итоговый Sol-review
node scripts/ralph/ralph-loop.mjs --run
```

Старые команды через `.agents/ralph-loop.mjs` продолжают работать и запускают
ту же реализацию. Для новых инструкций используйте канонический путь
`scripts/ralph/ralph-loop.mjs`.

Для первого тренировочного запуска использовать `--once` и вручную проверить
изменения и commit. Для AFK запускайте `--run` из чистой консоли в корне
репозитория. Один процесс сам проходит очереди всех настроенных фаз, циклы
исправлений, отдельные итоговые review и закрытие milestones; параллельно второй
Ralph не запускайте.

## Восстановление AFK-запуска

Ralph хранит lock в `.git/ralph-loop/run.lock`, состояние в
`.git/ralph-loop/state.json`, а накопительный журнал в
`.git/ralph-loop/run.log`. Они не попадают в commit и остаются локально между
запусками. Lock не позволяет двум процессам одновременно менять одну ветку;
устаревший lock снимается только после проверки, что записанный процесс уже
завершён. В log попадает вывод всех стадий, поэтому причину ночной остановки
можно посмотреть после возвращения.

State фиксирует `phaseIndex`, лимит итераций текущей фазы, issue, commit и стадию
pipeline. Если процесс завершился
после реализации, commit, push или во время review, следующий `--run` продолжает
с подтверждённой стадии, а не реализует задачу повторно. Оставленный Ralph dirty
tree восстанавливается только при совпадении с сохранённым состоянием. Любые
посторонние незакоммиченные изменения по-прежнему считаются небезопасными и
останавливают запуск — не очищайте их автоматически через `reset`/`restore`.

Все внешние команды имеют wall-clock timeout из секции `runtime`: обычные
команды — `commandTimeoutMs`, проверки — `validationTimeoutMs`, сессии Codex —
`codexTimeoutMs`. На Windows отдельный command-runner завершает всё дерево
зависшей команды, чтобы после timeout не оставались фоновые `npm`/тестовые
процессы. Временные сетевые ошибки GitHub/Git повторяются
`networkRetryAttempts` раз с экспоненциальной задержкой от
`networkRetryBaseDelayMs`; число повторов review задаёт
`reviewRetryAttempts`. `maxPages` ограничивает безопасную постраничную выборку
GitHub, не обрезая очередь первой страницей.

## Защита от ошибок

Скрипт останавливается, если:

- не заполнен `prompt`, отсутствуют `phases` либо в фазе нет `milestone`/`branch`;
- текущая Git-ветка не совпадает с конфигом;
- перед `--once` или `--run` есть незакоммиченная работа;
- Codex не оставил изменений для commit;
- Codex попытался превысить `maxTurns`;
- внешняя команда превысила соответствующий wall-clock timeout;
- Codex сменил ветку, самостоятельно создал commit или изменил issue;
- оркестратор не смог создать ровно один commit или очистить рабочее дерево;
- независимый review не завершился по технической причине;
- milestone-review вернул FAIL без структурированных findings;
- достигнут `maxIterations`;
- GitHub, Git или Codex вернули ошибку.

Перед закрытием issue, push и PR выполняются npm scripts из
`validationScripts`. В AFK-конфигурации обязательны `format:check`, `lint`,
`build`, unit-тесты Ralph и API/web E2E. Если хотя бы одна проверка не прошла,
issue не закрывается и PR не создаётся.

Сессия реализации не должна дублировать этот полный прогон. Внутри development sandbox она
запускает только минимальные тесты затронутой области. Это особенно важно на
Windows: Playwright и тесты завершения процессов могут уже вывести PASS, но не
завершить дочерние dev-серверы внутри sandbox. Внешний command-runner Ralph
выполняет полный набор в одноразовых validation-контейнерах с корректным
управлением деревом процессов. Для
npm-команд внутри сессии используется `npm.cmd`, чтобы не обращаться к
PowerShell-обёртке `npm.ps1` и пользовательскому npm prefix вне workspace.

Независимый issue-review обязан закончить полный аудит до verdict и вернуть все
обоснованные замечания одним результатом. Он не должен останавливаться на первой
найденной проблеме или включать посторонний технический долг вне scope issue.

`--run` создаёт draft PR по умолчанию. Для обычного PR укажите
`"draftPullRequest": false`.

Лимит исправлений красных тестов задаётся полем `maxTestFixAttempts`. По
умолчанию это 5. После лимита Codex должен оставить диагностику в финальном
сообщении; issue остаётся открытой.

`maxTurns` применяется отдельно к сессии реализации и локальному review issue.
Для итогового review используется `milestoneReview.maxTurns`. `maxIterations`
ограничивает суммарное количество сессий реализации обычных и автоматически
созданных review-issues **в одной фазе**, включая перезапуски `--run`. Счётчик
обнуляется только после чистого PASS и сохранённого перехода к следующей фазе.
Это защита от обхода лимита перезапуском, роста контекста и бесконечного
fix-review цикла. Wall-clock timeout отдельно останавливает зависшие внешние
процессы, которые не создают новых шагов.

## Объём итогового PR

Milestone-review использует весь накопительный diff `branch` относительно
`baseBranch` как контекст, но создаёт findings только по требованиям title и
description текущего milestone и необходимым им интеграциям. Это защищает
накопительную ветку от задач чужих фаз. Новую фазу всё равно рекомендуется
вести в отдельной ветке от корректной базы: prompt-ограничение не переписывает
историю и не делает накопительный PR удобным для ручного merge-review.

> Временные результаты review внутри `.agents/` игнорируются. Конфигурация,
> правила, документация и скрипт Ralph отслеживаются Git.
