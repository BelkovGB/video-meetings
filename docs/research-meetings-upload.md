# Исследование: загрузка и хранение файлов встреч

**Исходный план:**
[`plan-meeting-file-upload-and-management.md`](plan-meeting-file-upload-and-management.md)
**Дата:** 2026-08-06

## Краткий вывод

Для текущего одноузлового MVP оптимален один авторизованный
`multipart/form-data`-запрос непосредственно в NestJS API. Multer должен писать
файл через `DiskStorage` во временный каталог на том же файловом томе, где
находится постоянное хранилище. После проверки файл атомарно переносится под
случайным внутренним именем, а его метаданные записываются в PostgreSQL.

Такой вариант соответствует существующему стеку, не держит файл размером до
1 ГиБ в памяти и не требует отдельного протокола загрузки. Его ограничение —
оборванную передачу придётся начинать заново. Поэтому локальный диск и один
HTTP-запрос следует считать решением для MVP, а не целевой production-
архитектурой.

При переходе к нескольким экземплярам API, эфемерной файловой системе или при
появлении требования возобновлять загрузку следует перейти на S3-совместимое
объектное хранилище и multipart upload по временным подписанным URL. Если
объектное хранилище недоступно, но возобновление обязательно, подходящей
альтернативой является протокол tus.

## Контекст проекта

На момент исследования проект использует:

- Next.js 16 и React 19 в `apps/web`;
- NestJS 11 с Express 5 и Multer 2.2 в `apps/api`;
- Prisma 6 и PostgreSQL 17;
- Bearer JWT, который web-клиент хранит в `sessionStorage`;
- один API-процесс без reverse proxy и без объектного хранилища в локальной
  конфигурации.

План требует принимать записи, транскрипты и документы размером до 1 ГБ,
показывать метаданные, разрешать скачивание владельцу и участникам и разрешать
удаление только владельцу.

В текущей Prisma-схеме есть только владелец встречи. Модели участника и связи
пользователя со встречей пока нет. Поэтому правило «владелец и участники могут
загружать и скачивать» невозможно выполнить только внутри файлового модуля:
сначала требуется минимальная модель `MeetingParticipant(meetingId, userId,
createdAt)` с уникальной парой `(meetingId, userId)`. Общий access service должен
возвращать роль `OWNER`, `PARTICIPANT` или `NONE`; только наличие активной записи
даёт права участника. Приглашения и управление составом встречи остаются за
отдельной функцией, но файловый модуль не должен создавать членство сам.

## Рассмотренные варианты

| Вариант                                         | Плюсы                                                                                                                         | Минусы                                                                                                  | Вывод                                                              |
| ----------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| NestJS `FileInterceptor` + Multer `DiskStorage` | Уже входит в текущий стек; потоковая запись на диск; встроенный лимит размера и multipart-частей; низкая стоимость реализации | Нет возобновления; весь трафик проходит через API; локальный диск привязывает файл к одному узлу        | Рекомендуется для MVP                                              |
| Прямое использование Busboy                     | Максимальный контроль над потоком и ранней проверкой первых байтов                                                            | Повторяет работу Multer; больше собственного кода очистки, обработки ошибок и multipart edge cases      | Не даёт достаточной выгоды для текущего проекта                    |
| tus                                             | Стандартное возобновление по смещению; клиент продолжает загрузку после обрыва; есть расширения checksum и expiration         | Новые endpoints и состояния незавершённых загрузок; усложнение авторизации, очистки и тестов            | Использовать, только если resumable upload нужен до object storage |
| S3-compatible multipart upload по presigned URL | API не проксирует гигабайтный поток; повторно передаются только упавшие части; горизонтальное масштабирование                 | Нужны объектное хранилище, SDK, CORS, завершение/отмена multipart-сессий и очистка незавершённых частей | Целевая production-архитектура                                     |
| Buffer/Base64 в JSON или файл в PostgreSQL      | Простой формальный контракт                                                                                                   | Большое потребление RAM, увеличение payload при Base64, тяжёлые backup/restore и нагрузка на БД         | Не использовать                                                    |

NestJS официально строит поддержку `multipart/form-data` для Express на Multer и
предоставляет `FileInterceptor`. Сам Multer предупреждает, что `MemoryStorage`
хранит весь файл в `Buffer` и при больших файлах может исчерпать память. Поэтому
для лимита 1 ГиБ допустим только дисковый или внешний потоковый storage engine.

## Рекомендуемая архитектура MVP

### HTTP-контракт

Базовый контракт следует привязать к встрече:

| Метод    | Маршрут                                              | Назначение                                  |
| -------- | ---------------------------------------------------- | ------------------------------------------- |
| `POST`   | `/meetings/:meetingId/files`                         | Загрузить один файл в multipart-поле `file` |
| `GET`    | `/meetings/:meetingId/files`                         | Получить метаданные файлов встречи          |
| `POST`   | `/meetings/:meetingId/files/:fileId/download-ticket` | Создать одноразовую ссылку для скачивания   |
| `GET`    | `/file-downloads/:ticket`                            | Скачать файл по короткоживущему ticket      |
| `DELETE` | `/meetings/:meetingId/files/:fileId`                 | Удалить файл владельцем встречи             |

Успешная загрузка возвращает `201 Created` и представление файла:

```json
{
  "id": "cm...",
  "name": "retrospective.mp4",
  "category": "video",
  "mimeType": "video/mp4",
  "sizeBytes": 734003200,
  "uploadedAt": "2026-08-06T10:00:00.000Z"
}
```

Рекомендуемые ошибки:

- `400 Bad Request` — отсутствует файл, передано несколько файлов или нарушен
  multipart-контракт;
- `413 Payload Too Large` — размер больше `1_073_741_824` байт;
- `415 Unsupported Media Type` — расширение, MIME или сигнатура не входят в
  allowlist;
- `404 Not Found` — встреча или файл отсутствуют либо пользователь не входит во
  встречу; одинаковый ответ не раскрывает существование чужой встречи;
- `403 Forbidden` — участник пытается удалить файл, принадлежащий доступной ему
  встрече;
- `503 Service Unavailable` — файловое хранилище недоступно, закончилось
  разрешённое место или достигнут лимит параллельных загрузок.

Ошибки должны сохранять принятую в NestJS форму `statusCode` и `message` и
добавлять стабильный машинный `code`, например `UPLOAD_TOO_LARGE`,
`UNSUPPORTED_FILE_TYPE` или `STORAGE_UNAVAILABLE`. Web-клиент не должен разбирать
текст сообщения.

### Проверка доступа до записи файла

JWT guard выполняется раньше interceptor, но проверка доступа к конкретной
встрече в CQRS handler произойдёт слишком поздно: к этому моменту Multer уже
может сохранить тело запроса. Поэтому до `FileInterceptor` нужен meeting access
guard, который по `meetingId` и `request.user.sub` подтверждает владельца или
участника.

Guard должен использовать общий сервис политики доступа, а не дублировать
Prisma-запросы. Та же политика применяется для списка, скачивания и удаления.
Контроллер остаётся тонким и передаёт операцию в CQRS handler после завершения
файлового interceptor.

### Поток загрузки

1. JWT guard проверяет токен.
2. Meeting access guard проверяет доступ до разбора тела.
3. Multer принимает только multipart-поле `file`, ограничивает количество
   файлов и размер и потоково пишет данные во временный каталог.
4. Ранний `fileFilter` отклоняет очевидно неподдерживаемое сочетание имени и
   заявленного MIME, но не считается достаточной проверкой содержимого.
5. После завершения записи сервис проверяет фактический размер, расширение и
   сигнатуру временного файла.
6. Access service повторно проверяет роль непосредственно перед фиксацией. Это
   закрывает ситуацию, когда участника удалили из встречи во время долгой
   передачи.
7. Сервис формирует независимые `MeetingFile.id` и случайный `storageKey`, затем
   переносит файл из временного каталога в постоянный. Оба каталога должны быть
   на одном томе, чтобы использовать атомарный `rename` и не копировать 1 ГиБ.
8. Prisma создаёт запись метаданных. Если запись не удалась, постоянный файл
   удаляется компенсационным действием.
9. Клиент получает метаданные только после успешной фиксации обоих ресурсов.

Multer 2.2 удаляет созданные им файлы при ошибке multipart parser, превышении
`fileSize` и прерывании запроса. Приложение всё равно отвечает за очистку после
ошибок, возникших позже: проверки сигнатуры, переноса или Prisma.

### Ограничения Multer

Для одного файла следует задать как минимум:

```ts
{
  limits: {
    fileSize: 1_073_741_824,
    files: 1,
    fields: 0,
    parts: 1,
  },
}
```

Точный лимит задаётся сервером. Проверка `file.size` в браузере нужна только для
быстрой обратной связи и не является защитной границей.

Встроенный NestJS `FileTypeValidator` в установленной версии проверяет magic
number через `file.buffer`. `DiskStorage` буфер не предоставляет, поэтому нельзя
одновременно использовать его безопасную потоковую запись и рассчитывать на
стандартный validator без fallback на недоверенный MIME. Для проверки временного
файла следует явно добавить прямую зависимость `file-type` и вызвать
`fileTypeFromFile`, либо реализовать эквивалентный validator над путём к файлу.

### Модель данных

Минимальная рекомендуемая модель `MeetingFile`:

| Поле           | Назначение                                                           |
| -------------- | -------------------------------------------------------------------- |
| `id`           | Публичный идентификатор записи                                       |
| `meetingId`    | Обязательный FK на встречу с индексом для списка                     |
| `uploadedById` | Пользователь, выполнивший загрузку, для аудита                       |
| `originalName` | Очищенное отображаемое имя, не используемое как путь                 |
| `storageKey`   | Уникальный случайный внутренний ключ                                 |
| `category`     | `audio`, `video`, `transcript` или `document`                        |
| `mimeType`     | MIME после серверной проверки                                        |
| `sizeBytes`    | Фактический размер; PostgreSQL `integer` достаточен при лимите 1 ГиБ |
| `status`       | `READY`, `DELETING`, `MISSING`; список возвращает только `READY`     |
| `createdAt`    | Серверное время загрузки                                             |

В БД не следует хранить абсолютный путь: он связывает данные с конкретным
развёртыванием и мешает сменить storage backend. Оригинальное имя также нельзя
использовать как имя файла на диске из-за коллизий, path traversal и специальных
имён разных ОС.

Файловые операции нужно скрыть за интерфейсом вроде `MeetingFileStorage` с
операциями `finalize`, `open` и `delete`. Локальная реализация работает с
файловой системой, будущая — с object key. В доменной модели и HTTP-ответах это
различие не видно.

`storageKey` должен содержать не менее 128 случайных бит, иметь уникальный индекс
в БД и не включать расширение или исходное имя. Сервис эксклюзивно создаёт
каталог `<storageKey>` без `recursive`; при `EEXIST` генерирует новый ключ, а
затем переносит файл в `<storageKey>/content`. Это исключает перезапись при
коллизии на разных ОС. Путь после `resolve` обязан оставаться внутри настроенного
storage root; сервис не следует по символическим ссылкам или Windows reparse
points.

## Валидация типов и безопасность

OWASP рекомендует сочетать allowlist расширений, проверку MIME, сигнатуру файла,
случайное имя хранения, лимит размера и хранение вне публичного webroot. Ни
расширение, ни присланный браузером `Content-Type`, ни magic number по отдельности
не дают достаточной гарантии.

Таблица ниже является рекомендуемым allowlist для реализации. Она используется
как default, если до начала разработки PRD явно не утвердит другой набор:

| Категория  | Расширение | Допустимый заявленный MIME                                                | Проверка содержимого               |
| ---------- | ---------- | ------------------------------------------------------------------------- | ---------------------------------- |
| Аудио      | `.mp3`     | `audio/mpeg`                                                              | MPEG audio signature               |
| Аудио      | `.m4a`     | `audio/mp4`, `audio/x-m4a`                                                | ISO BMFF с audio-compatible brand  |
| Аудио      | `.wav`     | `audio/wav`, `audio/x-wav`                                                | RIFF/WAVE                          |
| Аудио      | `.ogg`     | `audio/ogg`, `application/ogg`                                            | Ogg container                      |
| Видео      | `.mp4`     | `video/mp4`                                                               | ISO BMFF                           |
| Видео      | `.webm`    | `video/webm`                                                              | EBML/WebM                          |
| Видео      | `.mov`     | `video/quicktime`                                                         | QuickTime/ISO BMFF                 |
| Транскрипт | `.txt`     | `text/plain`                                                              | Текстовая политика ниже            |
| Транскрипт | `.vtt`     | `text/vtt`                                                                | Заголовок `WEBVTT`                 |
| Транскрипт | `.srt`     | `application/x-subrip`, `text/plain`                                      | Текстовая политика и структура cue |
| Документ   | `.pdf`     | `application/pdf`                                                         | PDF signature                      |
| Документ   | `.docx`    | `application/vnd.openxmlformats-officedocument.wordprocessingml.document` | ZIP/OOXML container                |

`category` не передаётся клиентом: сервер выводит её из строки allowlist после
успешной проверки. Для контейнерных форматов одной общей ZIP или ISO BMFF
сигнатуры недостаточно; validator должен проверить ожидаемый container brand или
обязательные OOXML entries.

Для plain-text форматов нет надёжного magic number. Для них требуется строгая
проверка расширения и MIME, ограничение имени и запрет нулевых байтов; при
необходимости можно дополнительно проверять, что начало файла декодируется как
текст. HTML, SVG и исполняемые форматы не следует включать в категорию
«документ».

Дополнительные меры:

- хранить temp и final каталоги вне `apps/web/public` и не раздавать их через
  `express.static`;
- при выдаче и погашении download ticket проверять текущий доступ
  `issuedToUserId` и сопоставлять `fileId` с `meetingId` в одном запросе;
- возвращать `Content-Disposition: attachment` с безопасными `filename` и
  `filename*`, `Content-Length` и `X-Content-Type-Options: nosniff`;
- не собирать путь конкатенацией с пользовательским вводом;
- для локального MVP разрешать не более одной активной загрузки на пользователя
  и четырёх на процесс; до приёма тела требовать `Content-Length`, проверять, что
  он не превышает прикладной лимит с multipart overhead, и сохранять минимум
  2 ГиБ свободного места сверх принимаемого запроса;
- под тем же process-wide semaphore атомарно резервировать весь `Content-Length`:
  новый запрос допускается, только если `freeBytes - activeReservations` не
  опустится ниже 2 ГиБ; reservation освобождается при успехе, ошибке, abort и
  закрытии соединения;
- не логировать тело, JWT, исходное содержимое и подписанные URL;
- до публичного multi-user запуска добавить per-user/per-meeting storage quota и
  rate limit как конфигурируемую продуктовую политику;
- в production помещать недоверенные PDF/DOCX в карантин и не переводить в
  `READY` до антивирусного сканирования. Если MVP запускается без сканера, это
  должно быть явно принято как временный риск закрытого окружения.

## Согласованность файловой системы и PostgreSQL

Файловая система и PostgreSQL не участвуют в общей транзакции. Полностью убрать
аварийные окна без дополнительного состояния невозможно, поэтому MVP должен
использовать компенсацию и reconciliation:

- неуспешная валидация — удалить temp-файл;
- неуспешный `rename` — не создавать метаданные;
- неуспешный Prisma create после `rename` — удалить final-файл;
- при старте или по расписанию удалять просроченные temp-файлы и final-файлы без
  соответствующей записи;
- если связанный final-файл исчез или повреждён, переводить запись в `MISSING`,
  исключать её из списка/скачивания и создавать operational alert;
- для удаления в транзакции переводить запись в `DELETING`, затем удалять
  объект и только после этого удалять строку. При ошибке строка со `storageKey`
  остаётся скрытой от списка, а worker повторяет удаление.

Temp-файлы именуются `<uuid>.part`. Процесс хранит active set, а cleaner удаляет
только неактивные `.part` с `mtime` старше 24 часов. Orphan final-файл можно
удалить только после успешного запроса к БД и только если он старше 24 часов —
это исключает окно между `rename` и Prisma create. При недоступной БД cleaner
ничего не удаляет. Для одноузлового MVP job запускается в одном процессе;
появление нескольких реплик является сигналом перейти к object storage.

Удаление встречи должно сначала провести все её файлы через тот же
`DELETING`-workflow. Прямой каскад БД, удаляющий `MeetingFile`, запрещён, потому
что он оставит физические файлы без `storageKey`. Удаление пользователя может
обнулить `uploadedById`, но не должно удалять файл встречи.

## Скачивание больших файлов

NestJS `StreamableFile` принимает Node.js `Readable`, поэтому скачивание нужно
строить на `createReadStream`, а не `readFile` или `Buffer`. Это сохраняет
постоянное потребление памяти независимо от размера файла. Поддержка HTTP Range
для текущего сценария скачивания необязательна; она станет нужна для media
playback или возобновляемого скачивания.

Текущая Bearer-аутентификация создаёт отдельную проблему: обычная ссылка или
переход браузера не могут добавить JWT из `sessionStorage`, а `fetch` с
последующим `response.blob()` может потребовать память порядка размера файла.
Для MVP следует выбрать одноразовый download ticket, не меняя всю схему
аутентификации.

Bearer-защищённый `POST .../download-ticket` повторно проверяет доступ и создаёт
256-битный случайный token, сохраняя в PostgreSQL только его SHA-256 hash,
`fileId`, `issuedToUserId` для аудита, `expiresAt` (`now + 60 секунд`) и `usedAt`.
Потоковый
`GET /file-downloads/:ticket` атомарно отмечает token использованным, проверяет
срок, привязку к файлу и то, что `issuedToUserId` всё ещё имеет доступ к встрече,
затем отдаёт только `READY`-файл. Сам ticket является короткоживущим bearer
capability: проверка роли отсекает отозванный доступ, но не устанавливает личность
фактического предъявителя. Защиту от перехвата обеспечивают высокая энтропия, TTL
и одноразовость. Повторное использование возвращает `404`; для повтора
пользователь запрашивает новый ticket. Ответ содержит
`Cache-Control: private, no-store` и `Referrer-Policy: no-referrer`, а access logs
должны маскировать token в URL.

JWT в query string использовать нельзя: он попадает в историю, логи и
аналитику. Создание Blob допустимо только как временное упрощение для небольших
файлов и противоречит заявленному максимуму 1 ГиБ.

## Web-клиент и прогресс

Для MVP не нужна дополнительная upload-библиотека. `FormData` и
`XMLHttpRequest` покрывают выбор файла, drag-and-drop, Bearer header, прогресс и
отмену:

- `xhr.upload.onprogress` предоставляет `loaded` и `total`;
- `xhr.abort()` отменяет запрос;
- завершение передачи байтов ещё не означает успех API, поэтому после 100%
  интерфейс должен показывать состояние «обработка» до ответа `201`;
- повтор после сетевой ошибки начинает файл заново, что нужно явно сообщить
  пользователю;
- клиентская проверка размера и расширения должна использовать те же значения,
  что и API, но сервер остаётся источником истины.

Upload не следует проксировать через Next.js route handler: это добавит второй
серверный hop, ограничения времени выполнения и лишний поток данных. Браузер уже
обращается к NestJS API напрямую, а CORS для `Authorization` настроен на стороне
API.

## Настройки окружения и инфраструктуры

Для локальной реализации нужны как минимум:

- `UPLOAD_DIR` — абсолютный путь постоянного хранилища;
- `UPLOAD_TEMP_DIR` — абсолютный путь временного каталога на том же файловом
  разделе;
- `UPLOAD_MAX_BYTES=1073741824` и `UPLOAD_MIN_FREE_BYTES=2147483648`;
- `UPLOAD_MAX_REQUEST_BYTES=1074790400` — файл плюс 1 МиБ на единственную
  multipart-часть; guard требует `Content-Length` не выше этого значения, а
  Multer отдельно применяет точный лимит файла;
- проверка при запуске: создать каталоги с минимальными правами, разрешить real
  paths, подтвердить containment, запись и одинаковое устройство/том; при любой
  ошибке не запускать API;
- persistent volume в production-подобном окружении.

Любой reverse proxy должен пропускать тело немного больше 1 ГиБ, потому что
multipart envelope добавляет служебные байты. При Nginx значение
`client_max_body_size` по умолчанию равно `1m`; лимит proxy следует поставить
чуть выше прикладного, а точную границу оставить Multer. Для upload location
следует отключить `proxy_request_buffering`, иначе Nginx сначала полностью
запишет тело во временный файл, а затем API запишет его повторно.

Нужно согласовать timeout между браузером, ingress/proxy и Node.js. Ограничение
должно учитывать медленную загрузку 1 ГиБ и отслеживать отсутствие прогресса, а
не вводить слишком короткий общий timeout.

## Переход к production storage

Переход с локального диска необходим при выполнении любого условия:

- API запускается более чем в одном экземпляре;
- контейнер или файловая система эфемерны;
- нужен CDN, дешёвое долговременное хранение или независимые backup policies;
- обрывы гигабайтных загрузок становятся заметной пользовательской проблемой;
- API bandwidth или disk I/O становятся узким местом.

Предпочтительный production-поток:

1. Клиент запрашивает у API создание upload session, передавая имя, размер и
   ожидаемый тип.
2. API проверяет встречу, лимит и allowlist и инициирует multipart upload в
   S3-compatible storage.
3. API выдаёт короткоживущие presigned URL для частей.
4. Браузер отправляет части напрямую, повторяя только неуспешные.
5. API завершает multipart upload в private quarantine prefix: до завершения S3
   не предоставляет собранный объект для чтения.
6. API сверяет фактический размер, checksum, ключ и сигнатуру/структуру готового
   карантинного объекта, затем запускает антивирус.
7. После успешной проверки API копирует/promote-ит объект в рабочий key и
   проверяет destination. Только затем транзакция создаёт или переводит
   `MeetingFile` в `READY`, после чего карантинная копия удаляется. Ошибка
   promotion оставляет сессию `QUARANTINED` или переводит её в `FAILED`, но не
   публикует строку без готового объекта; некорректный объект удаляется.
8. Незавершённые сессии истекают и принудительно abort-ятся lifecycle job.

Production multipart state хранится отдельно от готового `MeetingFile` в
`MeetingFileUpload`: `id`, `meetingId`, `issuedToUserId`, storage `uploadId` и
`key`, ожидаемые размер/тип/checksum, `status` (`UPLOADING`, `QUARANTINED`,
`FAILED`), `expiresAt` и timestamps. `MeetingFile` создаётся либо переводится в
`READY` только после проверки; list/download никогда не читают upload session.

AWS рекомендует multipart upload для объектов от 100 МБ, то есть большая часть
видеозаписей из этого сценария естественно попадает в эту модель. Storage
interface и независимый `storageKey` позволяют перейти к ней без изменения
списка файлов и доменных правил доступа.

## План проверок реализации

### API и файловая система

- владелец и участник загружают разрешённый файл и видят корректные метаданные;
- пользователь вне встречи получает отказ до появления temp-файла;
- участник, удалённый из встречи во время передачи, не проходит повторную
  проверку и не фиксирует файл;
- участник не может удалить файл, владелец может;
- отсутствующий и чужой `meetingId` неразличимы по ответу;
- принимается файл ровно `1_073_741_824` байта и отклоняется файл на один байт
  больше;
- тест лимита использует уменьшенный конфиг, чтобы e2e suite не создавал
  гигабайтный fixture;
- отклоняются несколько файлов, неизвестное поле, spoofed MIME, двойное
  расширение, path traversal в имени и несоответствие сигнатуры;
- прерывание соединения, ошибка валидации, ошибка `rename` и ошибка Prisma не
  оставляют доступной записи или временного файла;
- два файла с одинаковым исходным именем не конфликтуют;
- скачивание идёт потоком с корректными заголовками и без роста памяти на размер
  файла;
- download ticket одноразовый, истекает через 60 секунд, привязан к файлу и
  хранит пользователя выдачи только для аудита;
- `DELETING` не показывается в списке и сохраняет `storageKey` до успешной
  физической очистки;
- reconciliation не затрагивает активные или связанные с БД файлы и переводит
  строку без физического файла в `MISSING`.

### Web-интерфейс

- выбор и drag-and-drop запускают один и тот же upload flow;
- прогресс обновляется, после 100% показывается серверная обработка;
- отмена переводит элемент в понятное состояние и не добавляет файл в список;
- ошибки размера, типа, доступа, сети и сервера различаются;
- успешный файл появляется в списке без полной перезагрузки страницы;
- сценарии проверяются на desktop и mobile через Playwright согласно проектным
  инструкциям.

### Нагрузочная проверка

- несколько параллельных загрузок не увеличивают heap пропорционально размеру
  файлов;
- медленный клиент не блокирует остальные запросы;
- заполнение диска возвращает контролируемую ошибку и не повреждает уже
  сохранённые файлы;
- измеряются длительность, число активных загрузок, объём принятых данных,
  ошибки по категориям и остаток свободного места без записи исходных имён в
  высококардинальные metric labels.

## Изменения, необходимые в исходном плане

Перед реализацией стоит уточнить план следующими техническими задачами:

1. Реализовать или явно запланировать модель участников и общий meeting access
   policy до обещания доступа участникам.
2. Добавить temp lifecycle, компенсационную очистку и reconciliation, а не
   только `upload_dir`.
3. Зафиксировать точный allowlist расширений/MIME и значение лимита в байтах.
4. Проверять доступ до файлового interceptor.
5. Выделить storage interface, чтобы локальный диск не проникал в CQRS handlers
   и HTTP representation.
6. Добавить одноразовый download ticket, чтобы скачивание не требовало 1-ГБ Blob
   или JWT в query string.
7. Добавить инфраструктурные лимиты, timeout и мониторинг свободного места в
   Definition of Done для production deployment.
